# i18n FR/EN bilingual

Tukio is bilingual **from day one**, not "FR-first then EN later". Every
user-facing string must be translatable; the backend dispatches templates
by `meta.locale`.

ADR-013 mandates `next-intl` for frontend i18n. The override of the
acquisition doc's `K-05` (FR slugs) is documented in
`.agents/context/code-style.md` (the `Language` section).

## Frontend (`next-intl`)

### Locale routing

URL shape: `/{locale}/...` where `locale ∈ {'fr', 'en'}`. Default `fr`.

```
/                          # redirect to /fr or /en based on Accept-Language
/fr/services/tentes-chapiteaux/wedding-marquees
/en/services/tents-marquees/wedding-marquees
```

The slug after `/services/` is the **language-specific** slug from
`category_translations.slug`, **not** the EN-canonical category slug.
This is intentional for SEO hreflang. Story 7.2 wires `hreflang` link
tags systematically.

### Message files

Per app, under `apps/<app>/messages/`:

```
apps/customer/messages/
├── fr.json          # French copy
└── en.json          # English copy
```

Keys MUST match across both locales (CI lint enforced in Story 7.7). No
key in `fr.json` may be missing from `en.json` and vice versa.

### Usage

**Server Component** (default):

```tsx
import { getTranslations } from 'next-intl/server';

export default async function BookingConfirmation() {
  const t = await getTranslations('booking.confirmation');
  return <h1>{t('title')}</h1>;
}
```

**Client Component** (`'use client'`):

```tsx
import { useTranslations } from 'next-intl';

export function BookingCta() {
  const t = useTranslations('booking');
  return <Button>{t('cta.bookNow')}</Button>;
}
```

### Hard rules

- **Zero hardcoded user-facing text** in components. Even short labels
  (`'OK'`, `'Annuler'`) go through `t()`.
- **No dynamic key composition** (`t(\`label.${variant}\`)`) — `next-intl`
  static analysis can't track them. Use ICU select / plural messages
  instead.
- **Interpolation via `t(key, { name })`** — never string concatenation.
- **Plurals via ICU**: `'You have {count, plural, one {# message} other {# messages}}'`.
- **Dates / numbers** via `useFormatter()` / `getFormatter()` — never
  `Intl.DateTimeFormat` directly.
- **Locale switcher** is a global pattern in `@tukio/ui/patterns/TopBar`
  (the locale toggle wires `next-intl`'s locale router).

### `messages.json` shape

Group keys by feature / screen, kebab-case for top-level groups, camelCase
for sub-keys:

```json
{
  "booking": {
    "confirmation": {
      "title": "Votre réservation est confirmée",
      "subtitle": "Le pro vous contactera sous 24 h"
    },
    "cta": {
      "bookNow": "Réserver maintenant",
      "viewCart": "Voir le panier"
    }
  }
}
```

`en.json` mirrors the structure exactly:

```json
{
  "booking": {
    "confirmation": {
      "title": "Your booking is confirmed",
      "subtitle": "The pro will reach out within 24h"
    },
    "cta": {
      "bookNow": "Book now",
      "viewCart": "View cart"
    }
  }
}
```

## Backend (`@tukio/i18n-client` + template dispatch)

### Locale propagation

- `gateway-api` reads the locale from the URL or `Accept-Language` header
  and emits `meta.locale` on every response envelope (see
  `.agents/context/rest-envelope.md`).
- NATS event consumers (notification-svc consuming
  `identity.user.registered.v1`, etc.) receive the locale via event
  payload or header. Templates dispatch on it.

### Resend email templates

Per template:

```
apps/notification-svc/src/infrastructure/external/resend/templates/
├── user-registered/
│   ├── fr.html        # French version (mjml or React Email source)
│   ├── en.html        # English version
│   └── index.ts       # Selects by locale + interpolates variables
```

The "send email" use case takes `{ locale: 'fr' | 'en', variables: {...} }`
and the adapter picks the template. Story 5.4 introduces Resend.

### Error messages

`DomainException` instances carry stable `tukioCode` + EN `title` /
`detail`. When surfaced through the envelope, `meta.locale` lets the
filter swap `title` / `detail` to the user's locale via a static map
(per service) or via i18n keys (V1+).

At MVP, the rule is:

- **Errors that the user sees** (validation, business rules): `title` and
  `detail` are translated via the locale dispatch table.
- **Errors that go to logs only**: stay EN.

## Glossary (FR business term → EN identifier)

See `.agents/context/glossary.md`. Adding a new French business term to
the codebase requires adding it to the glossary first.

## Slugs in URLs

The URL slug is **language-specific** (FR slug for FR URLs, EN slug for
EN URLs). The **canonical identifier** in the database is English.

```
/fr/services/tentes-chapiteaux            # FR slug 'tentes-chapiteaux'
/en/services/tents-marquees               # EN slug 'tents-marquees'
                                          # → both resolve to category.slug = 'tents-marquees'
```

`category_translations` table:

| category_id | locale | slug                | name                  | description |
| ----------- | ------ | ------------------- | --------------------- | ----------- |
| `uuid-1`    | `fr`   | `tentes-chapiteaux` | `Tentes & chapiteaux` | ...         |
| `uuid-1`    | `en`   | `tents-marquees`    | `Tents & marquees`    | ...         |

Routing logic (Story 3.10+):

1. Visitor hits `/fr/services/tentes-chapiteaux`.
2. Resolve `(locale='fr', slug='tentes-chapiteaux')` → `category_id=uuid-1`.
3. Load listings via `category_id`.
4. Emit `hreflang="en"` pointing to `/en/services/tents-marquees`.

This is why every entity that has a slug also has a `<entity>_translations`
table (categories, sub_categories, listings, etc.).

## Anti-patterns to refuse

- **Hardcoded `<p>Texte</p>`** in a component. Always `t('key')`.
- **`if (locale === 'fr') return 'Texte'`** branches in components.
  Use translation files.
- **Storing translations in a JS object next to the component.** Use
  `messages/{fr,en}.json`.
- **English-only `title` / `detail` in user-visible `DomainException`.**
  Wire the locale dispatch.
- **Translating a `tukioCode`.** It's a stable EN identifier — never
  localised.
